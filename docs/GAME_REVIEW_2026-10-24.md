### H-01 · P1 — 저장 실패 시 거래 취소와 복구 기록이 달라짐

**관찰:** 상점·제작 등의 `transact()`는 저장에서 예외가 나면 화면의 프로필을 이전 상태로 되돌린다. 그러나 계정 저장은 복구 기록을 먼저 쓰고 기본 저장 내용을 쓴다. 두 번째 쓰기가 실패하면 복구 기록에는 거래 후 상태가 남는다.

**재현:** 시작 골드 100 → 거래를 모사해 10 차감 → 기본 저장 쓰기 실패 → 화면과 기본 저장은 100으로 복귀했지만 복구 기록은 **90**이었다. 다음 연결에서 같은 수정 버전의 복구 기록을 채택할 수 있으므로, 사용자가 실패했다고 본 작업이 나중에 반영될 수 있다. 기존 저장 테스트도 두 쓰기 사이 중단 시 새 진행도를 복구하도록 설계돼 있어 UI 취소 정책과 합의가 필요하다.

**개선:** 저장의 확정 시점을 정하고, 확정 전 실패와 확정 후 캐시 실패를 구분한다. 복구 기록을 유효한 거래 결과로 인정하면 화면도 그 결과를 유지하고 안내해야 한다. 거래를 취소한다면 해당 거래의 복구 기록도 함께 취소돼야 한다. 단순히 복구 기록을 모두 지우는 방식은 전송 중인 다른 진행도를 잃을 수 있으므로 피한다.

**완료 기준:** 각 저장 단계에 실패를 넣어도 화면·새로고침 후 기록·최종 서버 기록이 같은 거래 결과를 보여야 한다.

### H-02 · P2 — 기기 저장 전용 플레이의 이전 정상 기록 보존

**관찰:** `LocalSaveRepository`는 하나의 키를 교체한다. 개별 쓰기는 원자적으로 처리되지만 이전 정상본을 따로 유지하지 않는다. 손상 내용은 검출하고 원본을 남기며, 계정 플레이에는 별도의 클라우드·캐시 복구가 있다. 보완 대상은 **기기 저장 전용 경로의 복구 선택지**다.

**개선:** 검증된 이전 정상본을 제한된 개수로 보존하고, 읽기 실패 화면에서 원본 내려받기와 정상본 복원을 제공한다. 저장 공간이 부족할 때 백업 생성 실패 때문에 정상 원본까지 잃지 않도록 처리한다. 사용자가 선택하지 않은 새 게임으로 자동 대체하지 않는다.

**완료 기준:** 기본 저장에 잘못된 JSON을 넣어도 원본을 내려받고 이전 정상본을 선택해 이어 할 수 있어야 한다. 계정과 기기 저장의 복구 대상을 혼동하지 않아야 한다.

**완료 기준:** 정상적인 후위 대기와 이동 불능을 구별할 수 있고, 표시를 위해 목표 판단을 매 프레임 다시 실행하지 않아야 한다.

### T-01 · P1 — 손상된 저장 내용이 초기 상태로 저장될 수 있음

**관찰:** 인증 쪽 검사는 버전 번호만 확인한다. 성장 데이터 변환은 잘못된 숫자를 최솟값으로 바꾼다. 이후 시작 과정에서 자동 저장을 실행한다. 버전이 3인 손상 자료는 읽기 오류로 분류되지 않아, 원본 백업 없이 초기화에 가까운 결과를 기기와 클라우드에 저장할 수 있다.

**재현:** `version:3`이고 레벨·경험치·돈 등에 잘못된 문자열이 있는 자료를 읽혔다. `storageOK`는 참으로 남았고 **레벨 1·돈 0**으로 저장됐으며, **백업 0개·클라우드 저장 대기 1건**이었다. 실제 읽기·변환·시작 시 저장 코드를 사용하고 화면과 저장소만 모의 처리했다.

**개선:** 필수 필드 손상과 이전 버전의 정상적인 누락을 구분한다. 손상 원문을 보존하고 자동 저장·클라우드 전송을 막은 뒤 복구 선택을 제공한다. 알 수 없는 미래 버전도 자동 새 게임으로 변환하지 않는다. 정상적인 1·2버전 이관은 유지한다.

**완료 기준:** 잘못된 JSON, 손상된 3버전, 지원하지 않는 미래 버전이 원본을 덮어쓰지 않아야 한다. 정상적인 구버전 자료만 명시된 이관 과정을 거쳐 저장돼야 한다.

### T-02 · P2 — 창을 벗어나도 경기 진행 상태가 유지됨

**관찰:** 창 포커스를 잃으면 키와 터치 입력을 해제하지만 `playing`은 유지한다. 렌더링 반복문에도 문서 숨김에 따른 경기 정지 조건이 없다. 따라서 게임 창이 보이는 상태에서 다른 창을 조작하면 선수가 멈춘 채 경기가 진행될 수 있다. 숨긴 탭의 실제 진행량은 브라우저의 프레임 제한에 따라 달라진다.

**재현:** 등록된 blur 입력 콜백 실행 후 눌린 키는 없어졌지만 `playing=true`가 유지됐다. 이는 콜백 확인이며 실제 창 전환 플레이를 촬영·측정한 결과는 아니다.

**개선:** 창 전환·문서 숨김 시 경기 일시정지와 입력 해제를 함께 수행한다. 돌아왔을 때 “경기 재개”를 직접 눌러 이어가게 한다. 이미 있는 수동 일시정지 기능과 기권 대화상자의 정지 처리를 공통 함수로 정리하면 된다. 경기 중 열 수 있는 업데이트 창도 같은 정지 정책에 포함한다.

**완료 기준:** 랠리·서브·득점 대기 중 다른 창이나 탭으로 이동해도 의도하지 않은 실점이 없고, 돌아온 직후 자동 타격이나 이동이 발생하지 않아야 한다.

### T-03 · P2 — 저장 성공 후 응답 유실을 다른 기기 충돌로 처리

**관찰:** 서버는 기대한 수정 버전과 일치할 때 저장하고 버전을 올린다. 저장은 성공했지만 응답만 유실되면 클라이언트는 이전 버전으로 재시도한다. 같은 요청을 알아보는 식별자가 없어 자신의 저장과 충돌할 수 있다.

**재현:** 수정 버전 1에서 서버가 저장해 2가 된 뒤 응답만 끊었다. 클라이언트의 두 번째 요청은 버전 1이었고, “다른 기기의 새 기록”으로 처리돼 후속 클라우드 저장이 차단됐다. 다른 기기는 없었다. 기기 기록은 유지되므로 이것을 즉시 데이터 소실로 판단하지는 않는다.

**개선:** 요청별 고유 ID를 서버에 기록하고 같은 요청의 재전송에는 기존 성공 결과를 반환한다. 또는 응답 유실 뒤 원격 자료를 다시 읽어 동일한 저장이 반영됐는지 확인한 후 조정한다. 실제 다른 기기의 변경을 덮어쓰는 무조건 재시도는 피한다. 용사월드의 요청 식별자 방식이 참고가 된다.

**완료 기준:** 서버 반영 후 응답 유실·중복 요청에서도 같은 저장이 한 번만 확정되고, 실제 다른 기기 충돌은 기존처럼 사용자 선택으로 해결돼야 한다.

### T-04 · P2 — 움직임 줄이기를 타격 연출 전체에 적용

**관찰:** 오라와 점수 효과에는 시스템의 움직임 줄이기 설정을 반영한다. 그러나 타격 시 카메라 흔들림·시야각 변화·화면 섬광 경로에는 같은 제한이 없다.

**개선:** 효과 강도를 한곳에서 결정하고, 움직임 줄이기에서는 흔들림과 순간적인 시야각 변화를 제거하며 섬광을 크게 낮추거나 끈다. 판정·점수·타이밍 안내는 그대로 제공한다. 효과 설정 때문에 경기 규칙이나 충돌 시간이 달라지지 않도록 시각 효과와 시뮬레이션을 구분한다.

**완료 기준:** 설정을 켠 상태에서 일반 타격·정타·라이징 스매시·득점 모두 화면이 흔들리지 않고, 타격 성공 여부는 소리와 안내로 알 수 있어야 한다.

## 5. 공통 추가 개선안

### C-01 · P3 — 키 설정과 안내 일원화

현재 키를 코드에서 직접 검사하는 경로가 있다. “이동 / 기본 공격 / 강한 공격 / 물약 / 필살기 / 일시정지”처럼 게임 행동을 정의하고, 키와 화면 버튼을 같은 행동에 연결하면 변경과 점검이 쉬워진다. 키 변경·중복 확인·기본값 복원·기기별 저장을 추가할 수 있다.

기본 조작은 유지하고 변경 기능을 선택 사항으로 제공한다. 게임패드 지원은 별도 필요가 있을 때 추가한다. 설치한 스킬을 모두 적용하기 위해 기능을 늘릴 필요는 없다.

**완료 기준:** 키를 바꾸면 화면 안내도 함께 바뀌고, 메뉴·입력창에 집중한 동안 전투 행동이 발생하지 않아야 한다.

### C-02 · P3 — 측정 결과를 남기고 병목만 개선

성능 저하를 이번에 실측하지 않았으므로 “최적화하면 몇 % 빨라진다”는 수치는 제시하지 않는다.

| 게임 | 먼저 이용할 측정 수단 | 측정 뒤 검토할 후보 |
| --- | --- | --- |
| 용사월드 | 개발 모드의 `perf=1`, `qa=perf-crowd`, `qa=perf-stress`, `qa=perf-spells`; 기존 p95·p99 프레임 및 엔진·장면·저장 시간 지표 | 동료·적·투사체가 많은 상황의 병목. HUD는 이미 약 100ms 간격으로 갱신하므로 매 프레임 갱신 문제로 오진하지 말 것. 필요하면 변한 값만 갱신 |
| 탁구왕 | 기존 `renderCost`와 함께 프레임 간격·p95·장면별 버텍스 수·업로드 크기를 기록 | 매 프레임 동적 배열·Float32Array 생성, 동적 버퍼 전송. 반복 할당과 GPU 전송이 실제 병목일 때 버퍼 재사용·정적 구조 분리 |

동일한 기기·화면 크기·장면에서 변경 전후를 비교한다. 보통 목표 60fps에서는 프레임 전체 예산이 약 16.7ms라는 점을 참고하되, CPU에서 측정한 렌더 함수 시간만으로 GPU 처리 시간이나 실제 표시 프레임을 판단하지 않는다. 저사양 기기용 목표는 별도로 정한다.

**완료 기준:** 측정 조건과 전후 결과를 기록하고, 저장·판정·조작이 달라지지 않은 상태에서 목표한 지표가 개선돼야 한다.
